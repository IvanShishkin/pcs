# Проверка соответствия PCS

Реализация может называться Product Control System, если выполняются все обязательные
условия ниже. Подробное обоснование требований приведено в
[методологии](methodology.md).

| Идентификатор | Требование |
|---|---|
| `PCS-BND-001` | Граница plant определена явно |
| `PCS-SET-001` | Setpoint и порядок разрешения конфликтов операционализированы |
| `PCS-SAF-001` | Safety invariants технически проверяются |
| `PCS-MOD-001` | Controller получает версионируемую model с указанным происхождением |
| `PCS-SEN-001` | Свидетельства отделены от оценки состояния, а доступ к ним регулируется |
| `PCS-DEC-001` | Воздействию предшествует неизменяемый план |
| `PCS-AUT-001` | Авторизация связана с идентичностью, планом, областью и сроком действия |
| `PCS-EXE-001` | Эффекты идемпотентны либо имеют определённую семантику повторных попыток |
| `PCS-VER-001` | Результат проверяется независимо от кода завершения actuator |
| `PCS-EVO-001` | Изменение контракта определяет множество затронутых потребителей по карте связей в model; выпуск согласован между ними |
| `PCS-LRN-001` | Каждый случай имеет итог обучения |
| `PCS-AUD-001` | Решение и эффекты воспроизводимы по журналу аудита; записи связаны с идентификатором случая |
| `PCS-DRF-001` | Расхождения model обнаруживаются и доводятся до исхода |
| `PCS-BRG-001` | Аварийный доступ ограничен, аудируется и создаёт последующий случай |
| `PCS-MET-001` | Качество controller измеряется по уровню риска |

## Результат проверки

Для каждого требования реализация фиксирует один из статусов:

- `pass` — выполняется и подтверждено свидетельством;
- `partial` — выполняется не для всей заявленной области;
- `fail` — не выполняется;
- `not-applicable` — неприменимость обоснована и зафиксирована.

Оценка без ссылки на проверяемое свидетельство не считается подтверждением соответствия.
