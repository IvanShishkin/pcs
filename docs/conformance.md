# Проверка соответствия PCS

Реализация может называться Product Control System, если выполняются все обязательные
условия ниже. Подробное обоснование требований приведено в
[методологии](methodology.md).

| Идентификатор | Требование |
|---|---|
| `PCS-BND-001` | Граница plant определена явно |
| `PCS-SET-001` | Setpoint выражен через измеримые цели, допустимые диапазоны и порядок разрешения конфликтов |
| `PCS-SAF-001` | Safety invariants технически проверяются |
| `PCS-MOD-001` | Controller получает актуальную версионируемую model; происхождение и срок актуальности критичных утверждений известны |
| `PCS-SEN-001` | Свидетельства отделены от оценки состояния; для них указаны источник, целевая среда, область измерения и состояние получения (`success`, `partial` или `fail`) |
| `PCS-SMP-001` | Для выборочных данных указаны число элементов и состояние полноты; ошибка или неизвестная полнота не выдаются за отсутствие отклонений |
| `PCS-TST-001` | Работоспособность sensors, проверок, interlocks и стратегий восстановления подтверждается после создания, существенного изменения и затем с периодичностью по риску |
| `PCS-DEC-001` | Воздействию предшествует план, который не изменяется после авторизации |
| `PCS-AUT-001` | Авторизация связана с идентичностью, планом, областью и сроком действия |
| `PCS-EXE-001` | Типизированные операции идемпотентны либо имеют определённые правила повторных попыток и частичного исполнения |
| `PCS-VER-001` | Результат проверяется независимо от кода завершения actuator; перечислены все постусловия и применимые safety invariants с исходом каждого пункта |
| `PCS-VER-002` | Непроверенное постусловие не засчитывается как успех; непроверенный safety invariant нельзя принять как остаточный риск |
| `PCS-EVO-001` | Изменение контракта определяет множество затронутых потребителей по карте связей в model; выпуск согласован между ними |
| `PCS-LRN-001` | Каждый случай имеет итог обучения, сохранённый в доступном controller артефакте или задаче на его изменение |
| `PCS-HIS-001` | Опровергнутое утверждение исключено из принятия решений; запись об опровержении и свидетельства сохранены в истории или аудите |
| `PCS-AUD-001` | Решение и эффекты воспроизводимы по журналу аудита; записи связаны с идентификатором случая |
| `PCS-DRF-001` | Расхождения model обнаруживаются и доводятся до зафиксированного исхода |
| `PCS-INV-001` | Собственные sensors, actuators, стратегии и проверки PCS инвентаризированы и имеют способ проверки работоспособности |
| `PCS-CPY-001` | Для копий определены источник или протокол согласования, версия, срок допустимого отставания и порядок сверки (при отсутствии копий — `not-applicable`) |
| `PCS-RDY-001` | Перед действием подтверждаются действительность учётных данных и доступность необходимых каналов; истечение доступа обрабатывается как штатный failure mode PCS |
| `PCS-BRG-001` | Аварийный доступ ограничен, аудируется и создаёт последующий случай |
| `PCS-MET-001` | Измеряется минимальное ядро метрик: полная loop latency, доля успешных действий, частота вмешательств человека, частота обращений к аварийному доступу |

## Результат проверки

Для каждого требования реализация фиксирует один из статусов:

- `pass` — выполняется и подтверждено свидетельством;
- `partial` — выполняется не для всей заявленной области;
- `fail` — не выполняется;
- `not-applicable` — неприменимость обоснована и зафиксирована.

Оценка без ссылки на проверяемое свидетельство не считается подтверждением соответствия.
