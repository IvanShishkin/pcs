# Sensors и actuators «Витрины»

Источник: инвентаризация доступов / Актуально до: изменения доступов или состава
сервисов.

## Реестр sensors (3.3, 5.2)

Чтение свободно в границах случая на уровне «ограниченное исследование» (7.1).
Каждое измерение сохраняется файлом в `evidence/` случая с источником, временем,
областью и состоянием получения.

| Sensor | Класс | Доступ | Область | Проверка работоспособности | Владелец |
|---|---|---|---|---|---|
| Prometheus | телеметрия | HTTP API, служебный токен только чтение | метрики всех сервисов | запрос `up` возвращает все 7 сервисов | платформа |
| логи `webhook-worker` | журналы | агрегатор логов, только чтение | ротация: хранятся 40 минут | тестовая строка при старте worker видна в агрегаторе | платформа |
| Postgres `orders` RO | проверка согласованности | роль `pcs_ro`, только `SELECT` | таблицы `orders`, `shipment_tasks`; поля с ПД — только по обоснованию в случае | `SELECT 1` через роль; попытка `UPDATE` отклоняется | backend |
| API провайдера | событие внешней системы | ключ из хранилища секретов, только чтение статусов | статус платежа по идентификатору заказа | запрос известного оплаченного заказа возвращает `captured` | backend |
| health-endpoints | телеметрия | HTTP внутри сети | `/health` каждого сервиса | все семь отвечают 200 | платформа |
| обращения поддержки | обращения людей | API службы поддержки, только чтение | тикеты за выбранный период | известный тестовый тикет читается | поддержка |
| API склада | событие внешней системы | HTTP внутри сети | резервы по отгрузочным заданиям | запрос известного задания возвращает резерв | склад |

Правило тишины (3.3): пустой результат засчитывается только при состоянии получения
`success`. Недоступность агрегатора, ошибка роли, тайм-аут API — это `fail`, а не
«отклонений нет».

Проба чувствительности выполнена для метрики `paid_without_shipment` один раз после
создания: тестовый заказ, оплаченный без отгрузочного задания, поднял метрику через
2 минуты. Регламентная периодичность не установлена — см. `PCS-TST-001` в матрице.

## Каталог операций (5.6, 7)

Изменяющие действия выполняются только через типизированные операции внутри случая
с планом и авторизацией. Поля `type`, `risk`, `scope`, `reversibility` — входные
данные для решения оператора; `authorization`, `max_attempts`, `timeout`, схема
параметров исполняются технически, параметр вне схемы отклоняется.

| Операция | Тип | Эффект | Обратимость | Область | Данные | Критичность | Уверенность | Режим |
|---|---|---|---|---|---|---|---|---|
| `noop` | runtime | нет | обратимое | нет | публичные | обычное | детерминированная | per-action |
| `restart-worker` | runtime | перезапуск `webhook-worker` | обратимое | служба | внутренние | обычное | детерминированная | pre-approved |
| `resync-payment-status` | data | сверка статуса оплаты с провайдером и создание отгрузочного задания | компенсируемое | набор сущностей, ≤ 500 заказов | внутренние | повышенное | детерминированная | per-action |
| `notify-customers` | communicate | уведомление покупателей по шаблону | необратимое | набор сущностей, ≤ 500 заказов | персональные | повышенное | детерминированная | per-action |

Режим авторизации выведен из сочетания измерений (7), а не назначен операции
напрямую: `restart-worker` получает pre-approved как обратимая операция над
службой без состояния; обе операции над набором заказов — per-action из-за
компенсируемости, персональных данных и области.

### `resync-payment-status`

- **Параметры:** `order_ids` (список, 1–500, шаблон идентификатора заказа).
- **Предусловия:** каждый заказ в статусе `paid_unconfirmed`; API провайдера
  доступен (проверка готовности, 9).
- **Эффект:** для заказа со статусом `captured` у провайдера — перевод в `paid`
  и постановка отгрузочного задания; заказ с иным статусом пропускается и
  перечисляется в отчёте.
- **Постусловие (проверять независимо):** у каждого переведённого заказа ровно
  одно отгрузочное задание — запрос к Postgres `orders` RO, не отчёт операции.
- **Откат:** невозможен; компенсация — пометка заказа `manual_review` без
  движения денег.
- **Повтор:** идемпотентна по идентификатору заказа; максимум 3 попытки,
  частичное исполнение допустимо — обработанные заказы перечисляются в отчёте.
- **Ограничение времени:** 10 минут.

### `notify-customers`

- **Параметры:** `order_ids` (список, 1–500), `template` (перечисление:
  `delay`, `resolved`).
- **Предусловия:** время в часовом поясе покупателя вне 23:00–08:00; заказ ещё
  не получал это уведомление.
- **Эффект:** постановка уведомления в очередь `notify-service`.
- **Постусловие (проверять независимо):** число доставленных уведомлений равно
  числу заказов — по журналу доставки `notify-service`.
- **Откат:** невозможен; компенсация — уведомление `resolved`.
- **Повтор:** не повторяется автоматически; недоставленные передаются в
  поддержку.
- **Ограничение времени:** 5 минут.

### `restart-worker`

- **Параметры:** нет.
- **Предусловия:** `webhook-worker` нездоров по health-endpoint или логам.
- **Постусловие (проверять независимо):** health-endpoint отвечает 200, в
  логах нет цикла падений в течение 5 минут.
- **Откат:** не требуется.
- **Повтор:** идемпотентна; максимум 3 попытки, дальше эскалация.

## Аварийный доступ (7.1)

Действие вне каталога выполняет оператор руками. Команда и вывод фиксируются в
случае, событие `breakglass` записывается в журнал аудита, после закрытия случая
создаётся случай на типизацию операции. Отдельной команды для записи события нет —
см. `PCS-BRG-001` в матрице.
