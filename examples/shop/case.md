# CASE-20260415-01 — оплаченные заказы не передаются на склад

Структура случая: `case.md`, `evidence/` (неизменяемые файлы свидетельств),
`plans/plan-N.md` и `plans/plan-N.auth.yaml`. Здесь всё сведено в один файл;
содержимое свидетельств сокращено до строк, по которым принималось решение.

## Вход

- Сигнал: метрика `paid_without_shipment` = 37 при пороге 5 (бизнес-инвариант B1);
  два обращения в поддержку «оплатил, статус не меняется».
- Источник: Prometheus, служба поддержки. Время: 2026-04-15T09:31Z.
  Корреляция: оповещение `B1-paid-without-shipment`, тикеты SUP-4410, SUP-4412.
- Цель случая: все оплаченные заказы получают отгрузочное задание; покупатели с
  задержкой дольше часа уведомлены.

## Estimate

- **Факты:** worker не работал в интервале, накрывающем создание 37 заказов; после
  рестарта новые webhooks обрабатываются; у провайдера 35 из 37 заказов оплачены.
- **Выводы:** webhooks по 35 заказам пришли во время простоя worker и потеряны. По
  model провайдер повторяет доставку в течение 24 часов — тогда заказы должны были
  восстановиться после 09:12, но не восстановились. Либо утверждение model неверно,
  либо повторы ещё не пришли.
- **Неизвестное:** причина `OOMKilled` (логи за 08:38–08:55 недоступны); фактическая
  политика повторов провайдера; были ли повторно обработаны webhooks заказов,
  созданных после 09:12.
- **Конкурирующие гипотезы:** ротация ключа подписи webhooks — опровергнута:
  после 09:12 webhooks принимаются с той же подписью (свидетельство 03).
- **Уверенность:** высокая в причине потери; низкая в политике повторов провайдера.
  Актуально до: изменения интеграции с провайдером.

Два заказа со статусом `pending` из случая исключены: оплата не завершена,
инвариант B1 к ним не применим.

## Decide

План: `plans/plan-1.md`. Цель — перевести 35 заказов в `paid` с отгрузочными
заданиями и уведомить покупателей о задержке.

Операции плана:

1. `resync-payment-status` с `order_ids` — 35 заказов из свидетельства 04 со
   статусом `captured`.
2. `notify-customers` с теми же `order_ids`, `template: delay`. Время 09:40Z,
   ограничение 23:00–08:00 не нарушено ни для одного часового пояса покупателей.

Рассмотренные альтернативы и причины отказа:

- ждать повторной доставки webhooks: политика повторов провайдера не подтверждена,
  задержка уже превышает час, продуктовая policy требует уведомления;
- запросить повторную отправку у провайдера: у провайдера нет такого API
  (свидетельство: документация провайдера, раздел webhooks);
- ручная обработка поддержкой: 35 заказов, оценка два часа, без независимой проверки;
- `restart-worker`: worker уже работает, эффекта не даст.

Классификация плана по измерениям (7): эффект — изменение; обратимость —
компенсируемое; область — набор сущностей, 35 заказов; данные — персональные
(уведомления); критичность — повышенное; уверенность — детерминированная.
Режим: per-action.

Предусловия: заказы в `paid_unconfirmed` (02); API провайдера доступен (04).
Постусловия и safety invariants — в разделе Verify. Откат: компенсация
`manual_review` для заказов, у которых после операции нет ровно одного задания.
Ограничение времени: 15 минут на план. Повторы: по policy операций.

## Learn

Исход: **model обновлена.**

- `plant.md`, неуправляемые зависимости: утверждение «провайдер повторяет доставку
  webhooks 24 часа» опровергнуто — по документации провайдера три повтора в течение
  10 минут. Запись исправлена, прежняя формулировка и свидетельство 03 сохранены в
  истории изменений.
- `failure-modes.md`: новый режим отказа — потеря webhooks при простое worker дольше
  10 минут; стратегия — `resync-payment-status` по заказам за период простоя.
- Пробел наблюдаемости: простой worker не поднимает оповещение, ротация логов в 40 минут
  скрывает причину. Задача на sensor «время с последнего обработанного webhook»
  поставлена в очередь на автоматизацию с частотой: один случай за период наблюдения,
  экспертная оценка ущерба — высокая.
- Новый случай CASE-20260415-02: причина `OOMKilled` worker. Причинная связь между
  памятью и простоем не установлена, в этот случай не входит.

Сверка model при закрытии: `sensors-actuators.md` фактам не противоречит; в
`plant.md` исправлена одна строка (выше).

Случай закрыт 10:41Z после фиксации итога обучения и записей аудита.
