# Plant «Витрина»

Источник: инвентаризация репозиториев и продуктивной среды / Актуально до: изменения
состава сервисов или платёжного провайдера.

## Граница (методология 4.1)

### Продукты и компоненты

| Компонент | Роль | Управляем |
|---|---|---|
| `storefront` | веб-витрина, корзина, оформление заказа | да |
| `catalog-service` | товары, цены, остатки для показа | да |
| `order-service` | заказы, статусы, история | да |
| `payment-adapter` | приём webhooks провайдера, сверка статусов оплаты | да |
| `webhook-worker` | обработчик очереди webhooks | да |
| `warehouse-service` | отгрузочные задания, резерв остатков | да |
| `notify-service` | письма и push покупателям | да |

### Среды исполнения

`production` (единственная управляемая), `staging` (только для проверки гипотез;
результаты переносятся в production как гипотеза, 5.3).

### Хранилища и классы данных

| Хранилище | Данные | Класс |
|---|---|---|
| Postgres `orders` | заказы, статусы оплаты, отгрузочные задания | внутренние; контакты и адреса — персональные |
| Postgres `catalog` | товары, цены, остатки | публичные |
| Redis `queue` | очередь webhooks и уведомлений | внутренние |
| Объектное хранилище `media` | изображения товаров | публичные |
| Хранилище секретов | ключи провайдера, ключи подписи webhooks | секреты |

### Неуправляемые зависимости

| Зависимость | Что наблюдаемо | Что не управляемо | Стратегия |
|---|---|---|---|
| платёжный провайдер | статус платежа по API, доставка webhooks (повторы: три в течение 10 минут) | повторная доставка webhooks, доступность API | сверка статусов по запросу; деградация: заказ ждёт подтверждения; эскалация при недоступности API > 30 мин |
| служба доставки | статус отправления по API | сроки, отказы | наблюдение; эскалация в поддержку |
| CDN | доступность витрины снаружи | кэш, маршрутизация | обход на прямой адрес по решению оператора |

### Внешние стороны, способные изменять состояние

- платёжный провайдер: статусы платежей;
- операторы склада: ручная смена статуса отгрузки в админке;
- служба поддержки: ручная отмена и возврат по регламенту;
- разработчики: аварийный доступ по SSH (break-glass, аудит обязателен).

## Иерархия setpoints (4.2)

### 1. Safety invariants (4.3)

| Код | Инвариант | Проверка |
|---|---|---|
| S1 | ни одна операция PCS не создаёт повторного списания или возврата | техническая: у операций нет доступа к API списаний; после операции над оплатой сверка числа capture по провайдеру |
| S2 | PCS не инициирует движения денег | техническая: каталог операций не содержит `refund` и `capture`; policy запрещает параметры вне схемы |
| S3 | персональные данные читаются только в границах случая и минимально | процедурная: в случае фиксируется, какие поля прочитаны; техническая проверка отсутствует |
| S4 | единственная копия данных не уничтожается | техническая: у служебной идентичности нет прав `DROP`, `TRUNCATE`, `DELETE` на `orders` |
| S5 | миграция схемы только при наличии свежей резервной копии | процедурная: план обязан ссылаться на копию не старше 24 ч |

### 2. Бизнес-инварианты

| Код | Инвариант | Sensor |
|---|---|---|
| B1 | каждый оплаченный заказ получает ровно одно отгрузочное задание не позже чем через 15 минут | метрика `paid_without_shipment` |
| B2 | остаток товара не отрицателен | проверка согласованности `catalog` ↔ `warehouse` раз в час |
| B3 | статус заказа меняется только вперёд по жизненному циклу | триггер в `orders` |

### 3. SLO и error budget

| Показатель | Цель | Окно |
|---|---|---|
| доступность оформления заказа | 99,9 % | 30 дней |
| задержка обработки webhook, p95 | < 5 минут | 7 дней |
| error budget доступности | 43 минуты | 30 дней |

Допустимый режим деградации: при недоступности провайдера оформление заказа
продолжается, оплата переводится в статус «ожидает подтверждения».

### 4. Продуктовые policy

- покупатель получает уведомление, если оплаченный заказ не передан на склад
  дольше часа;
- уведомления не отправляются с 23:00 до 08:00 по часовому поясу покупателя;
- сверка оплаты по API провайдера допускается не чаще одного раза в минуту на заказ.

### 5. Цель случая

Задаётся в самом случае и не может противоречить уровням выше. Конфликт разрешается
верхним уровнем; неразрешимый — эскалируется оператору.
