# alertfox-control — первая установка PCS: что сработало и что нет

Продукт: AlertFox (alertfox.ru) — платформа мониторинга сайтов. Установка: репозиторий
`alertfox-control`, controller — Claude Code при операторском тактировании, оператор и
supervisory level — один человек. Период: 2026-07-11 … 2026-07-13.

Документ описывает фактический ход первой установки, включая нарушения методологии,
допущенные при её построении. Он является свидетельством, а не нормой; правки,
вытекающие из этого опыта, внесены в `docs/methodology.md` (§3.3, §12, §13) и
`docs/conformance.md` (`PCS-SEN-002`, `PCS-BLD-001`, `PCS-IND-001`).

## Что построено

- Model: граница plant, карта контрактов, иерархия setpoints (5 safety invariants,
  3 бизнес-инварианта), 5 режимов отказов, каталог sensors с канареечными целями.
- Runner `bin/op` — единственная санкционированная точка исполнения: проверяет план,
  авторизацию (SHA-256 плана + срок), policy, схемы параметров, лимиты попыток; ведёт
  hash-chain журнал аудита. 55 тестов.
- Каталог из 6 операций, policy допуска, скиллы цикла `/case`, `/verify`, `/close`.
- Три случая: два реальных, один синтетический (репетиция полного цикла).

## Нарушения методологии, допущенные при построении

Все они — нарушения текста, который был открыт у автора реализации во время работы.
Это главный результат установки: **прозаическое требование не удерживает даже того,
кто его читает.**

### Порядок построения нарушен (§12, §3.3)

Actuators (журнал аудита, policy, runner, каталог операций) построены задачами 2–6.
Model — задачей 7. Измерение plant (инвентаризация прода) — задачей 9. То есть
шаг 6 порядка построения выполнен раньше шагов 3, 4 и 5.

Цена: model, написанная по чтению репозиториев вместо измерения plant, оказалась
неверна почти во всех прод-фактах. Пользователь SSH (`deployer`) не существовал;
DNS-endpoints имели другой метод и путь; проверка SSL принимала другой параметр;
схема релизов лендинга была другой; порт сканера был опубликован наружу, а не на
localhost. Главное: ядро обращалось к сканеру безопасности на **отдельном сервере**,
которого в model не было вообще.

### Каталог наполнен прежде случаев (§3.2)

Шесть операций написаны из пяти режимов отказов, придуманных за столом. Первый
реальный инцидент не покрыла ни одна: `restart-service` перезапускал контейнер,
которым продуктив не пользовался, `rollback-landing` оказался неисполним (обёрнутый
скрипт интерактивен и ждёт ввода). Фактическое покрытие каталога на первом случае — 0.

### Тишина sensor принята за исправность (§5.2)

Функция сканирования безопасности была мертва 13 дней: внешний сервер не отвечал,
поллер ядра каждую минуту получал таймаут (≈13 700 записей в журнал в сутки), новых
результатов сканирования не появлялось. Обнаружено случайно, при проверке
постороннего вопроса. Правило «проверь живость sensor прежде, чем доверять его
молчанию» было записано в model установки — прозой, и не сработало.

### Соответствие оценено автором реализации (§15)

Первичная матрица соответствия заполнена тем же агентом, который писал реализацию.
Завышение обнаружено при перепроверке: статус `pass` по независимой проверке
результата опирался на журнал, который ведёт сам runner, — то есть свидетельство
порождено проверяемым механизмом.

Внешнее ревью, проведённое после этого, за один проход дало шесть подтверждённых
находок, из них две — способные привести к произвольному исполнению команд на
продуктиве (интерполяция параметра `ref` в удалённую команду) и к слежению за чужим
выпуском (выбор «последнего» run вместо своего). Ни одну из них не нашли ни автор,
ни 44 теста, покрывавшие runner, но не покрывавшие shell-скрипты actuator'ов.

## Что сработало

- **Исполняемые правила удержались все.** Каталог fail-closed (операция вне каталога —
  отказ), схемы параметров, hash-chain журнала, проверка TTY при авторизации. Проверка
  TTY сработала против самого агента: он предложил оператору способ авторизации, который
  runner отверг.
- **Дисциплина случая нашла инцидент.** Разбирая посторонний вопрос, controller обнаружил
  недоступность сканера, оформил свидетельствами и не потерял находку.
- **Свидетельства с происхождением.** Файлы `evidence/` с источником и временем позволили
  перепроверить выводы, не полагаясь на память агента.
- **Внешний оппонент дёшев и эффективен.** Шесть находок за один проход — дешевле любой
  внутренней проверки, которую делал автор.

## Итог

Установка выполнила критерий готовности (§12.1): реальный случай прошёл путь от Sense до
Learn внутри системы с полным аудитом. При этом сама система на момент первого инцидента
не обладала операционной наблюдаемостью, достаточной, чтобы этот инцидент заметить, —
её обнаружил человек, а не controller.

Вывод, вынесенный в нормативную часть: **всякое требование, которое может быть выражено
исполняемой проверкой, ТРЕБУЕТСЯ так выражать.** Прозаические требования методологии
нарушаются незаметно для самой реализации — и первой это делает та реализация, которая
методологию строит.
